# Phase 3 准入审批蓝图

## 交付结论

Phase 3 在现有 Phase 1/2 的 Vue 3 + NestJS + Prisma SQLite 单仓工程上增量完成，没有重建项目、替换技术栈或改写既有迁移。业务依据来自《无人快递车监管平台需求说明书》7.1—7.6、8.1—8.2，以及总提示词明确的 Phase 3 范围。

本阶段覆盖：企业入驻、路测申请、轻量流程定义、审批任务、审批处理、审批历史、审批结果、牌照发放与牌照续期。

## 业务语义与生命周期

申请是业务主对象；流程定义描述审批规则；每次提交创建新的流程实例。审批任务是某一节点对某一角色的待办，审批历史是不可覆盖的事实记录，审批结果是全部节点通过后形成的业务凭证。

```text
企业准备材料 → 保存草稿 → 提交申请 → 节点审批 → 查看结果 → 发牌/续期生效
                    │           ├─ 通过节点 → 下一节点
                    │           ├─ 退回补正 → 企业编辑并重提（新实例）
                    │           └─ 驳回 → 终止
                    └─ 审批中不可直接改写材料
```

| 状态 | 业务义务 | 允许动作 |
| --- | --- | --- |
| DRAFT | 企业补齐申请资料 | 编辑、提交 |
| IN_REVIEW | 当前审批角色必须作出决定 | 通过、退回补正、驳回 |
| RETURNED | 企业按意见补正 | 编辑、重新提交 |
| APPROVED | 审批结论已形成 | 路测申请可发牌；其他类型查看结果 |
| REJECTED | 本次申请结束 | 查看原因 |
| COMPLETED | 发牌等后续业务事件已完成 | 查看结果与关联牌照 |

“审批通过”和“牌照已发放”保持为两个不同事件。路测申请通过后由监管人员显式发牌，发牌完成后申请进入 `COMPLETED`；续期申请最终通过时，在同一事务内更新原牌照有效期。

## 用户故事地图（Phase 3 切片）

### 企业经办人

1. 准备申请：选择入驻、路测或续期；填写主体/路线/安全/牌照材料。
2. 提交申请：保存草稿；校验完整性；确认进入审批。
3. 跟踪进度：查看当前节点、审批意见和结果；退回后补正重提。
4. 使用许可：查看牌照、有效期和审批来源；临期时提交续期。

### 监管审批人员

1. 接收待办：只看到所辖组织及当前角色可处理的待办。
2. 审阅材料：在同一上下文查看申请对象、材料和既往轨迹。
3. 作出决定：通过、退回补正或驳回；退回/驳回必须写明意见。
4. 完成许可：最终节点形成审批结果；路测通过后发放车辆牌照。

### 本期与后续切片

- 本期：顺序审批、按角色派发、办理时限、退回补正、驳回、结果、发牌、续期。
- 后续：会签/加签的运行时语义、附件上传与签章、跨部门并行分支、消息催办、完整 BPMN 建模。

## 数据模型

| 模型 | 责任 |
| --- | --- |
| `AdmissionApplication` | 三类申请的主记录、快照字段、状态与当前节点 |
| `AdmissionApplicationVehicle` | 路测申请与车辆的多对多关系 |
| `ProcessDefinition` | 按申请类型、版本和启停状态管理流程 |
| `ProcessNodeDefinition` | 节点顺序、审批角色、时限、退回规则和会签模式元数据 |
| `ProcessInstance` | 每次提交/重提形成的独立运行实例 |
| `ApprovalTask` | 节点待办、办理人、意见、截止时间和处理状态 |
| `ApprovalHistory` | 提交、节点通过、退回、驳回、通过、发牌的不可变轨迹 |
| `ApprovalResult` | 审批文号、有效期、结果类型与关联牌照 |

## 权限与数据范围

- 企业端：服务端强制限定登录用户的 `enterpriseId`；企业管理员可创建、编辑、提交，企业普通用户只读。
- 监管端：超级管理员查看全量；其他监管角色查看本组织和直属下级组织申请。
- 待办：除数据范围外，还必须匹配节点 `approvalRoleCode`；拥有处理权限但角色不匹配仍返回 403。
- 写操作：全部进入审计日志。最终审批、续期改期、发牌与结果/历史写入使用数据库事务。
- 路测车辆和续期牌照：服务端再次校验归属，不信任前端传入企业标识。

## API

统一前缀 `/api/admission`：

- `GET /options`：按数据范围返回企业、车辆、牌照和活动流程。
- `GET/POST /applications`、`GET/PATCH /applications/:id`：申请列表、详情、草稿维护。
- `POST /applications/:id/submit`：完整性校验后创建流程实例和首个待办。
- `GET /tasks`、`POST /tasks/:id/handle`：审批工作台和节点处理。
- `GET/POST /workflows`、`PATCH /workflows/:id`：流程定义、启停和同类型活动版本切换。
- `POST /applications/:id/issue-license`：从已通过路测申请发牌并关联审批结果。
- `GET /licenses`：按范围查询牌照、车辆、企业、有效期和审批来源。

## 页面行为与恢复

- 集合页具有真实服务端搜索、状态筛选、分页、加载、失败重试和空结果。
- 草稿保存失败不关闭表单；严格按申请类型发送字段，避免无关空值触发错误校验。
- 提交与审批均有确认；审批中禁止直接修改，退回后原申请和意见保留。
- 审批抽屉把当前决策放在首屏，完整材料和历史作为同一上下文的证据。
- 退回/驳回意见为必填；重复处理同一任务由后端拒绝。
- 牌照发放成功后，结果同时在申请详情、牌照管理和车辆档案数据中可追溯。

## 已知边界

- 数据模型支持一次路测关联多车；本期 UI 限制一次申请选择 1 辆，确保“一申请—一审批结果—一发牌动作”的闭环清晰。批量分车发牌需扩展结果与牌照的一对多语义。
- 当前系统先有企业账号和企业主体，入驻申请用于激活/复核既有主体；面向未开户外部企业的匿名预申请与审批后自动建账号属于后续域扩展。
- `countersignMode`、`canReturn` 已进入流程元数据，但本期执行器为顺序单节点处理；会签/加签运行时和复杂 BPMN 明确不在 Phase 3。
- 附件采用材料说明字段和既有证照档案关联；对象存储上传、病毒扫描、电子签章不在本期。
