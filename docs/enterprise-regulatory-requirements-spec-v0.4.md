# 杭州市功能性无人车监管平台——企业侧与监管侧需求规格说明 V0.4

## 1. 文档目的

本文档在现有无人车监管系统功能和菜单基础上，定义企业侧、监管侧需要补充和调整的需求，用于产品评审、页面原型、数据模型、研发实施和测试验收。

V0.4 不重新设计一套与现有系统割裂的信息架构。现有一级模块名称、用户认知和主要权限边界原则上保留，只合并明显重复的二级页面，并将安全员、检查、信用、规则等新增能力放入最接近的现有模块。

市级、省级、国家级驾驶舱另立规格，不在本文档中展开。

## 2. 项目范围和已确认决策

| 决策项 | 本期结论 |
|---|---|
| 试点范围 | 杭州市，按 60 辆真实车辆建设 |
| 主管部门 | 平台内统一按杭州市交通运输局进行准入和运行监管 |
| 车辆类型 | 配送、环卫、巡逻、零售、接驳五类，并预留其他功能车 |
| 车辆编码 | 首期由平台自动生成默认统一编码 |
| 保险 | 本期不建设 |
| 远程操作 | 本期仅保留厂商/企业对外接口配置和测试能力，后续对接 |
| 监管车辆控制 | 不允许；监管只能向企业下达处置要求 |
| 事故规则 | 采用四级事故/事件及默认报告时限，可配置 |
| 信用规则 | 初始 100 分，采用本文件默认扣分、等级和修复规则 |
| 跨区域 | 本期不建设跨市、跨省备案、互认和数据交换 |
| 跨部门 | 仅生成建议推送部门和材料包，不建设联合办理流程 |
| 公众查询 | 本期不建设 |
| 数据留存 | 原始轨迹、视频、接口日志、事故证据默认 90 日；长期数据期限可配置 |
| 页面布局 | 参考用户提供的单卡片列表布局，查询在列表上方，新增/导入/导出位于列表右上角 |

## 3. 目标与非目标

### 3.1 建设目标

- 在现有系统基础上支持五类功能性无人车。
- 建立统一编码、一车一档和车辆全生命周期记录。
- 补齐安全员资格、排班、人车关系和数据接入能力。
- 补齐事故时限、证据保全、检查整改和信用修复闭环。
- 让监管处置要求由企业执行并反馈，监管负责监督和复核。
- 保持现有菜单和操作习惯，减少用户培训及代码迁移成本。

### 3.2 本期不建设

- 保险、保单、保额、到期提醒和理赔。
- 跨市、跨省备案、材料互认和事件转办。
- 公众订单、企业、车辆或监管信息查询。
- 监管侧直接向车辆发送停车、恢复、降级等控制指令。
- 完整厂商远程控制台、视频驾驶台和车端控制系统。
- 其他部门在本平台内会签、审批、执法或结案。
- 仅凭信用分自动停运、撤销许可或强制退出。

## 4. 角色模型

采用“少角色＋权限点＋数据范围＋资格属性”。

### 4.1 企业侧

| 角色 | 权限范围 |
|---|---|
| 企业管理员 | 企业资料、成员账号、车辆、材料、接口和全部企业业务配置 |
| 企业业务人员 | 申请、任务、车辆监看、事件处置、整改反馈；远程安全相关操作另受资格限制 |
| 企业只读人员 | 查看授权数据，不可提交、修改或执行操作 |

远程安全员是企业人员的资格属性，不是独立系统角色。相关操作必须同时满足业务权限、资格审核通过、资格有效、处于有效班次和车辆已分配。

### 4.2 监管侧

| 角色 | 权限范围 |
|---|---|
| 监管管理员 | 用户、机构、权限、业务规则、流程、信用和留存配置 |
| 监管业务人员 | 档案、审批、许可、运行监管、安全处置、检查、评价和报表 |
| 监管只读人员 | 查看授权辖区和业务范围，不可审批、配置或下达处置要求 |

经办、复核、发布、导出等高风险动作使用权限点控制，不为每个动作新增角色。

### 5.3 不作为菜单的内容

| 内容 | 页面内表达方式 |
|---|---|
| 到期许可 | 许可信息/许可管理的状态筛选 |
| 暂停、撤销、恢复 | 许可列表行内操作或批量操作 |
| 变更、续期、退出 | 申请类型或许可行内操作 |
| 待处理、处理中、已完成、已驳回 | 状态筛选或少量稳定 Tab |
| 车辆类型、运营场景 | 车辆字段；字典由业务规则配置 |
| 在线情况、车辆分布 | 实时运行/实时车辆的视图和筛选 |
| 事故证据、审批记录、操作日志 | 对象详情的局部视图 |

## 6. 页面布局与交互规范

### 6.1 列表页参考布局

除监管总览、企业运营工作台和地图态势页面外，所有业务列表页采用用户提供的“单一白色业务卡片”布局。

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│ 业务标题                                                                     │
│                                                                              │
│ 条件一 [输入/选择]  条件二 [输入/选择]  [查询] [重置]      [新增] [导入/导出] │
│ ──────────────────────────────────────────────────────────────────────────── │
│ 序号 │ 主要字段 │ 状态 │ 关联对象 │ 更新时间 │ …… │ 操作                 │
│ 数据 │ 数据     │ 状态 │ 数据     │ 时间     │ …… │ 查看 编辑 更多       │
│                                                                              │
│                                                               分页与总数     │
└──────────────────────────────────────────────────────────────────────────────┘
```

要求：

- 页面背景为浅灰工作区，主体为白色圆角业务卡片。
- 标题位于卡片左上角，只显示业务名称，不添加介绍性副标题。
- 查询条件和“查询、重置”位于列表上方左侧。
- “新增、导入、导出、更多操作”位于列表区域右上角。
- 查询和新增使用主按钮；重置、导出等使用次按钮。
- 工具栏与表格之间设置弱分隔线。
- 表头使用浅蓝或品牌色低饱和背景，正文保持白底。
- 操作列固定右侧，序号或选择列固定左侧。
- 分页位于表格底部并默认右对齐。
- 宽度不足时筛选条件换行，操作区整体换行并保持右对齐；表格横向滚动，不静默隐藏关键列。

### 6.2 页面内容约束

业务页面不得放置：

- “本页面用于……”等功能说明。
- 建设意义、产品价值、欢迎语和宣传语。
- 与当前任务无关的 Banner、说明卡片和装饰性 KPI。
- 把状态、属性、动作包装成菜单或独立说明页面。

必要帮助应出现在字段提示、错误反馈、确认弹窗和规则查看中。

### 6.3 查询与列表

- 常用条件直接显示，低频条件放入列表上方的“更多筛选”。
- 查询条件、排序、页码在进入详情并返回后必须保留。
- 无结果时显示“未找到符合条件的数据”并提供清除筛选入口。
- 行级操作超过 3 个时，低频操作收纳到“更多”。
- 批量操作仅在选中数据后启用，并显示选中数量和影响范围。
- 删除、停用、撤销、驳回、规则发布等高风险操作必须确认并说明后果。

### 6.4 新增、编辑与详情

- 字段少、风险低的操作使用弹窗；字段多或有分步校验时使用抽屉或独立表单页。
- 提交失败必须保留输入并定位错误字段或业务规则。
- 详情包含状态、关键字段、关联对象、时间线和当前可执行操作。
- 审批、处置和发布完成后显示明确结果及业务编号。

### 6.5 页面状态

所有页面需覆盖加载中、正常、只读、空数据、筛选无结果、接口失败、数据过期、部分失败和重试状态。

错误信息必须说明发生了什么、哪些输入已保留、下一步如何处理，不得只显示“操作失败”。

## 10. 车辆统一编码

默认格式：`330100-FV-YYYY-NNNNN-C`

| 段 | 含义 | 示例 |
|---|---|---|
| `330100` | 杭州市行政区划代码 | `330100` |
| `FV` | 功能性无人车固定标识 | `FV` |
| `YYYY` | 首次发码年份 | `2026` |
| `NNNNN` | 当年五位顺序号 | `00001` |
| `C` | Mod 11 校验位，可为 0-9 或 X | `7` |

示例：`330100-FV-2026-00001-7`。

- 编码不包含具体车辆类型，避免场景变化导致换码。
- 准入批准后由系统自动发码，企业只读。
- 监管管理员可冻结、注销或重新发码，但需填写原因并审计。
- 已注销编码不得重新分配。
- 后续行业编码通过映射接入，不改变历史平台编码。

## 11. 事故与事件默认 SLA

| 等级 | 判定示例 | 企业响应 | 平台首报 | 核心证据 | 后续报告 |
|---|---|---:|---:|---:|---:|
| I 级特别重大 | 死亡或重伤、火灾爆炸、车辆失控造成重大风险、重大社会影响 | 5 分钟 | 30 分钟 | 2 小时 | 24 小时初报，3 个工作日自查报告 |
| II 级重大 | 人员受伤、明显财产损失、道路长时间阻断、远程操作失败且风险未解除 | 10 分钟 | 1 小时 | 2 小时 | 24 小时初报，3 个工作日自查报告 |
| III 级一般 | 无人员伤亡碰撞、轻微财产损失、车辆需现场处置 | 30 分钟 | 2 小时 | 24 小时 | 3 个工作日事件说明 |
| IV 级运行异常 | 越界、超速、离线、紧急停车、系统降级且未造成事故 | 30 分钟 | 系统实时生成 | 当日补全 | 处置后 1 个工作日关闭或升级 |

- 人员伤害、财产损失、道路影响、技术失控和社会影响取最高等级。
- 情况不明时按较高等级上报，降级必须记录人员、依据和时间。
- 事故或重大异常自动建档并冻结事件时间窗数据。
- 平台 SLA 不替代报警、急救、现场防护和法定报告义务。

## 12. 信用积分默认方案

### 12.1 账户与等级

- 企业和车辆分别建立信用账户，初始分均为 100 分。
- 分值范围 0-100，不设置额外奖励分。
- 同一根因多个事件采用最高单项扣分，其他关联项累计不超过最高项的 50%。

| 等级 | 分值 | 默认监管建议 |
|---|---:|---|
| A 正常 | 90-100 | 常规监管和抽查 |
| B 关注 | 75-89 | 增加提醒和数据核查，建议提高抽查关注度 |
| C 高风险 | 60-74 | 重点监管，建议专项检查和续期人工复核 |
| D 严重 | 0-59 | 建议约谈、专项检查和运营资格复核；不得自动停运 |

### 12.2 默认扣分

| 级别 | 默认扣分 | 示例 | 生效方式 |
|---|---:|---|---|
| 轻微 | -2 | 一般超时、单次低质量上报、轻微规则违背且及时纠正 | 规则允许时自动记分 |
| 一般 | -5 | 重复数据异常、一般违规、整改逾期、单次无人值守 | 监管确认后生效 |
| 严重 | -10 | 无有效许可运行、安全员严重不合规、重大告警处置不当 | 经办确认并复核 |
| 重大 | -20 | 瞒报、篡改证据、重大事故有效责任结论、拒不执行有效要求 | 关联有效事实或决定并复核 |

- 调查中、申诉中或责任未明确的事件只标记待确认，不进入正式分值。
- 车辆技术事件没有企业责任依据时，不直接扣企业信用。
- 信用分只能自动触发提醒、风险标识和业务建议。

### 12.3 修复周期

| 级别 | 前置条件 | 观察期 | 恢复方式 |
|---|---|---:|---|
| 轻微 | 整改关闭 | 30 日无复发 | 自动恢复 |
| 一般 | 整改复核通过 | 90 日无复发 | 申请后监管确认 |
| 严重 | 专项整改和复查通过 | 180 日无复发 | 监管复核后恢复 |
| 重大 | 有效决定已履行、整改通过 | 365 日 | 专项审核决定，不自动恢复 |

修复通过新增恢复或冲正流水完成，不删除原扣分。暂停、撤销和退出必须另有有效依据和人工决定。

## 15. 60 辆试点容量

| 项目 | 设计值 |
|---|---:|
| 在册车辆 | 60 辆 |
| 同时在线车辆 | 最坏按 60 辆 |
| 常态上报 | 平均 1 Hz/车，可配置 |
| 短时峰值 | 5 Hz/车，即 300 条/秒，持续 5 分钟 |
| 单条遥测典型大小 | 不高于 2 KB，接口设置最大载荷 |
| 管理端并发用户 | 30 人 |
| 增长预留 | 数据模型不改造可扩至 200 辆，性能需复测 |
| 视频 | 事件触发上传，不做 60 路持续汇聚 |

性能验收：

- 60 辆以 1 Hz 连续上报 24 小时，无数据静默丢失和重复业务事件。
- 300 条/秒短时峰值下允许排队，但峰值后能够追平。
- 常用列表查询 95% 在 2 秒内返回。
- 地图首次加载 60 辆车辆 3 秒内可操作，增量更新不整页刷新。
- 30 个并发管理用户查询、审批和处置时无串权或明显阻塞。

## 16. 核心流程

### 16.1 准入与发码

`企业提交 → 自动校验 → 监管受理 → 审核/补正 → 复核 → 批准/驳回 → 系统发码 → 生效`

### 16.2 许可

`企业申请 → 预检 → 监管审查 → 批准/附条件批准/驳回 → 生效 → 运行监测 → 变更/续期/暂停/退出`

### 16.3 监管处置要求

`风险事件 → 监管核查 → 下达要求 → 企业确认 → 企业执行 → 反馈结果 → 监管复核 → 关闭/退回/升级`

### 16.4 事故证据

`事件建档 → 冻结数据 → 企业首报 → 证据包生成 → 企业补充 → 监管分析 → 整改 → 复核 → 归档/继续保全`

### 16.5 信用

`有效事件 → 扣分建议 → 确认/复核 → 信用流水 → 等级变化 → 监管建议 → 整改观察 → 修复/冲正`

## 17. 权限与安全

- 企业用户只能访问本企业及明确授权的数据。
- 企业管理员不能绕过安全员资格、班次和车辆分配执行受限操作。
- 监管人员可查看企业操作记录、下达处置要求，但没有车辆控制权限。
- 视频、轨迹、人员身份、接口密钥、事故证据和审计日志使用独立敏感权限。
- 规则发布、信用扣分、许可暂停/撤销、数据导出和留存期限缩短需要复核或二次确认。
- 接口凭证不可明文回显，测试与生产配置隔离。
- 所有敏感查看、导出、配置、审批和处置行为进入审计日志。

## 18. 非功能要求

### 18.1 数据可靠性

- 遥测写入支持幂等、乱序、时间校验和断点补传。
- 页面区分实时、延迟、离线和补传数据。
- 审批、事件、处置要求和信用流水不得因重试重复创建。
- 清理任务检查保全和引用关系，并生成清理结果。

### 18.2 规则与审计

- 分类、材料、流程、许可、安全员、事件、信用、接口和留存规则均版本化。
- 已发布规则不可直接覆盖修改。
- 规则命中展示输入事实、规则版本和输出。
- 历史业务继续引用当时规则版本。

### 18.3 可用性

- 企业侧和监管侧保持一致的查询、表格、详情和操作位置。
- 返回列表时保留查询、排序、页码和滚动上下文。
- 提交失败保留输入并给出具体修正方式。
- 无权限操作隐藏或禁用时说明原因。
- 所有操作支持键盘到达和明确焦点；窄宽度下表格横向滚动，不隐藏关键操作。

### 18.4 技术演进

- 现有 SQLite 可用于开发演示；正式生产前完成并发、备份和恢复评估。
- 业务、遥测、媒体和审计数据逻辑分层。
- 车辆增长至 200 辆或上报频率提升前重新压测。

## 19. 全局验收标准

1. 现有企业侧和监管侧一级模块名称保持不变。
2. 旧页面按第 5.4 节正确重定向并带入筛选条件。
3. 五类车辆均能完成备案、发码、申请、运行、安全和退出流程。
4. 业务列表页在一个白色圆角卡片内呈现标题、查询、操作、表格和分页。
5. 查询位于列表上方，新增、导入、导出位于列表右上角。
6. 页面不出现介绍性副标题、宣传内容和无关说明卡片。
7. 状态、属性和生命周期动作不单独建立菜单。
8. 平台编码自动生成、不可编辑、不可复用且不重复。
9. 监管侧无法直接向车辆发送控制指令。
10. 远程接口只展示配置、能力和测试状态，不伪装为生产执行成功。
11. 信用账户初始 100 分，扣分和修复符合第 12 章并可配置。
12. 信用分不能直接触发停运、撤销许可或退出。
13. 事故和重大事件保全数据不受 90 日默认清理影响。
14. 60 辆车辆 1 Hz 连续上报和 300 条/秒短时峰值通过验证。
15. 系统不存在跨市、跨省和公众查询入口。

## 20. 实施优先级

### P0：菜单与核心闭环

- 按第 5 章调整二级菜单和旧路由重定向，保留现有一级模块。
- 统一列表页布局、查询和操作位置。
- 支持五类车辆、场景、上装和统一编码。
- 合并申请、事件、评价等重复页面。
- 实现安全员资格、排班、人车关系和接口配置。
- 实现监管处置要求、四级事故 SLA、证据冻结和可配置留存。

### P1：监管增强

- 黑灰运行识别。
- 检查管理与整改闭环。
- 企业/车辆信用账户、扣分、申诉和修复。
- 建议推送部门和材料包。
- 远程操作接口模拟回执测试。

### P2：分析优化

- 企业和车辆安全画像。
- 统一分析与监管报表。
- 数据质量趋势和规则效果分析。
- 根据真实运行数据调整容量、事件和信用参数。

## 21. 成功指标

- 60 辆车辆档案完整率、编码冲突率和有效许可覆盖率。
- 五类车辆任务与备案场景一致率。
- 数据及时率、完整率、重复率和异常恢复时长。
- 告警确认、监管要求、企业执行和监管复核时长。
- 事故首报及时率、证据完整率和整改关闭周期。
- 安全员资格有效率、人车比异常率和无人值守时长。
- 信用扣分申诉率、冲正率、修复率和同类问题复发率。
- 菜单首次点击成功率、列表查询成功率、批量操作成功率和表单失败恢复率。

反向指标：不得出现监管越权控车、信用自动停运、旧路由失效、查询条件丢失、批量误操作、敏感数据越权或模拟回执被当作真实结果。
